
= Upgrade Kadalu

Here the steps to upgrade a Kadalu service to the latest version for Kubernetes.

== Upgrade kubectl-kadalu binary

[source,console]
----
$ curl -fsSL https://github.com/joejulian/kadalu/releases/latest/download/install.sh | sudo bash -x
$ kubectl-kadalu version
[...]
----

== Apply the Kadalu operator manifest

1. Download the relevant Kadalu operator manifest for your Kubernetes cluster:
 - Generic Kubernetes: https://github.com/joejulian/kadalu/releases/latest/download/kadalu-operator.yaml[kadalu-operator.yaml]
 - MicroK8s: https://github.com/joejulian/kadalu/releases/latest/download/kadalu-operator-microk8s.yaml[kadalu-operator-microk8s.yaml]
 - RKE: https://github.com/joejulian/kadalu/releases/latest/download/kadalu-operator-rke.yaml[kadalu-operator-rke.yaml]
 - OpenShift: https://github.com/joejulian/kadalu/releases/latest/download/kadalu-operator-openshift.yaml[kadalu-operator-openshift.yaml]
2. Apply the manifest to the cluster. Do not rewrite values in the released
   manifest before applying it.

[source,console]
----
kubectl apply -f kadalu-operator.yaml
----

The operator owns the CSI node and controller workloads. A separate
`csi-nodeplugin.yaml` release asset is not used.

== Upgrade node plugins safely

The node plugin intentionally uses the `OnDelete` update strategy. Replacing a
node-plugin pod also terminates the Gluster FUSE clients running in that pod,
so do not delete every node-plugin pod at once.

The operator intentionally remains unready and quiesces the CSI provisioner
until every desired node-plugin pod matches the new DaemonSet template. Start
the node-plugin rotation after the DaemonSet template has the expected image;
do not wait for the operator rollout first.

[source,console]
----
kubectl -n kadalu get daemonset kadalu-csi-nodeplugin \
  -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
kubectl -n kadalu get daemonset kadalu-csi-nodeplugin \
  -o custom-columns='GENERATION:.metadata.generation,OBSERVED:.status.observedGeneration,DESIRED:.status.desiredNumberScheduled,CURRENT:.status.currentNumberScheduled,UPDATED:.status.updatedNumberScheduled,READY:.status.numberReady,AVAILABLE:.status.numberAvailable,MISSCHEDULED:.status.numberMisscheduled,UNAVAILABLE:.status.numberUnavailable'
----

Remove misscheduled stale pods first, one node at a time during a maintenance
window. Safely drain the node, delete its node-plugin pod, and verify that no
replacement appears because the node is outside the current desired schedule.
After each deletion, `MISSCHEDULED` must decrease while `DESIRED`, `CURRENT`,
`READY`, and `AVAILABLE` remain unchanged. Stop if those invariants do not hold.
Use normal deletion and do not bypass graceful termination.

Then upgrade each desired outdated node one at a time:

. Cordon and safely drain the node according to your workload disruption
  policy.
. Delete only that node's `kadalu-csi-nodeplugin` pod.
. Wait for its replacement to become Ready and verify the node's storage
  workloads before uncordoning it.
. Repeat for the next node.

[source,console]
----
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets
kubectl -n kadalu delete pod <nodeplugin-pod>
kubectl -n kadalu wait --for=condition=Ready pod/<replacement-nodeplugin-pod> \
  --timeout=5m
kubectl uncordon <node>
----

Choose drain flags appropriate for the cluster. Stop and investigate any mount
or workload failure before continuing to another node.

Before proceeding, verify that `GENERATION` equals `OBSERVED`; `DESIRED`,
`CURRENT`, `UPDATED`, `READY`, and `AVAILABLE` are equal; `MISSCHEDULED` is
zero; and `UNAVAILABLE` is zero or omitted.

== Verify the controller workloads

After every desired node-plugin pod uses the new template and is Ready, wait
for the operator to resume the CSI provisioner and finish its rollout:

[source,console]
----
kubectl -n kadalu rollout status deployment/operator --timeout=75m
kubectl -n kadalu rollout status statefulset/kadalu-csi-provisioner --timeout=5m
kubectl -n kadalu get pods
----

Size the Helm, GitOps, and `rollout status` timeouts for the manual node
rotation plus serial reconciliation of every existing storage pool. The
operator Deployment's default 24-hour progress deadline is only a final
diagnostic backstop, not the normal maintenance timeout.
