= Release management

== Tag-driven release workflow

Releases are published only by the `Release` GitHub Actions workflow. Push a
canonical SemVer tag without a `v` prefix after the target commit has passed
the pull-request checks. For example:

[source,console]
----
git tag 1.36.0
git push origin 1.36.0
----

The workflow builds the release assets, verifies and publishes immutable
amd64/arm64 image tags, stages the GitHub release, and only then updates
`latest` for a stable version. Pre-release tags such as `1.36.0-rc.1` never
move `latest`.

The repository must have `DOCKER_USER` and `DOCKER_PASSWORD` Actions secrets,
and `DOCKER_USER` must match the repository owner. PyPI publication is skipped
unless this fork is explicitly configured with its own `TWINE_PASSWORD`; the
existing `kadalu-quotad` project name belongs to upstream.

Check the [Release URL here](https://github.com/joejulian/kadalu/releases)

== Local release preparation

`make prepare-release`, `make cli-build`, `make helm-chart`, and
`make pypi-build` may be used to inspect artifacts locally. `make release`
deliberately refuses to publish: a workstation build cannot atomically provide
the workflow's multi-architecture and immutable-tag guarantees.
